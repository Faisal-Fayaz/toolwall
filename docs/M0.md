# M0 spike — findings and go/no-go

**Verdict: GO.** The Rego/Wasm design holds. Six real issues surfaced; all were
fixable and are now encoded in the build tooling or documented here.

| # | Test | Result |
|---|---|---|
| T1 | OPA CLI 1.21.1 wasm loads in `opa-wasm@1.10.0` runtime | **PASS** — wasm ABI minor 3 |
| T1 | Argument-level decisions correct | **PASS** — 5/5, correct rule attribution |
| T2 | Eval latency | **PASS** — 0.081 ms/call (budget 5 ms) |
| T3 | Recompile on policy edit | **PASS** — 47–108 ms (budget 300 ms) |
| T4 | stdio MCP interception round-trips | **PASS** — 5/5 |

Reproduce: `npm test`

## The version matrix was the real risk

The plan flagged this as go/no-go. It turned out to matter, but not where expected:

- `opa-wasm` (npm) is at **1.10.0**; the OPA CLI is at **1.21.1**. Despite the
  skew, the runtime loaded CLI-1.21.1 output fine (wasm ABI minor 3). No pinning
  needed.
- The actual failure was elsewhere: **`opa_linux_amd64_static` at v1.10.0
  reports `WebAssembly: unavailable`**. v1.21.1's static build reports
  `available`. Pin the CLI to ≥ v1.21.1.
- `opa capabilities --current` reports `wasm_abi_versions: [1.1, 1.2]`, so the
  skew is handled by the runtime, not by us.

**Consequence for packaging:** OPA has no npm distribution. `scripts/fetch-opa.sh`
vendors the checksum-verified binary into gitignored `bin/opa`. The bundled
policy ships precompiled as `policy.wasm`, so the common case needs no OPA at
all; the CLI is only required to author custom `.rego`.

## Custom builtins require a capabilities file

OPA type-checks builtins, so any builtin implemented in Node must be declared
at compile time or the policy is rejected with `rego_type_error: undefined
function`. The decl needs `"type": "function"` — omitting it makes OPA reject
the *capabilities file itself* with a misleading "no such file" error.

`policy/capabilities.json` is therefore a contract between Rego and Node; keep
it in sync with `src/engine` host builtins.

## Rego v1 gotchas hit during the spike

1. **`"lit" in some_object` tests VALUES, not keys.** Both `"network" in obj`
   and `"command" in obj` returned `false` for an object having those keys.
   Use `object.get(obj, "lit", null) != null`. This is a silent-failure mode:
   the rule never fires and a `default decision` quietly returns the wrong
   *reason* for the right *effect*.
2. **Bare identifier object keys are variable references.** `name: "x"` inside
   an object literal yields `rego_unsafe_var_error`. Quote every key.
3. **`%q` is unavailable in `sprintf`.** The Wasm runtime backs it with
   `sprintf-js`, which lacks the Go verb. Use `%s`.

## opa-wasm@1.10 API differs from older docs

- Custom builtins are a **map passed as the 3rd argument to `loadPolicy()`**.
  There is no `registerBuiltin`.
- A builtin impl receives **spread positional args** (JSON-decoded) and
  **returns** a JSON-able value; the SDK handles marshalling. No result slot.
- `evaluate(input)` hits the baked-in entrypoint. There is no `setInput` /
  `eval("data.…")`.
- `evaluate()` returns an **array of result-sets**: `[{ result: <value> }]`.
  Unwrapping `raw[0].result` is required.

## Test-design lesson

The first version of the T1 assertions checked only `effect`. A never-firing
rule still yields the correct effect via `default decision`, so a completely
dead policy passed. Assertions now pin the **rule name** as well as the effect.
Worth applying to any policy test: verify the rule that fired, not just its
outcome.

## What this means for v0.1

The transport and policy layers are both de-risked and fast enough that neither
needs architectural change. Remaining v0.1 work is ordinary:

- engine module wrapping `loadPolicy` + host builtins
- decision log (JSONL, redact at write time)
- CLI (`toolwall record` / `replay`)
- `policy/default.rego` promoted from the spike fixture

Carry-forward risks, unchanged: **bash AST analysis (v0.4)** remains the one
component that can be evaded, and must not be presented as a security boundary.
